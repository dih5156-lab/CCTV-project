## 2. 일정에 반영할 가용시간

- **1D = 순개발 4시간**이라는 공수 단위는 유지한다. 하루 6시간은 최소 1.5D다.
- 주 5일을 가정하면 최소 주 30시간이다. 주 5일 자체와 휴무 일정은 미확정이다.
- 원계획 총공수 186시간은 주 30시간에서 약 6.2주, 추정 148~286시간은 약
  4.9~9.5주다. 상한에 20% 여유를 둔 약 343시간은 약 11.4주다.
- 이 수치는 **순개발 시간 환산**이며 현재 남은 공수의 재측정이나 납기 확정이 아니다.
  기존 계획은 코드 재사용을 이미 가정했으므로 기존 성과를 다시 이중 차감하지 않는다.
- 09-21~12-31 평일 74일에 6시간을 단순 곱하면 444시간이다. 공휴일·다른 업무·
  장비/부서 대기 전의 이론값이며 확보된 개발시간은 아니다.
- 현재 P0~P7 목표 기간은 유지한다. 더 확보된 시간은 검증·결함 대응 여유로 두고,
  실제 1주 투입시간과 잔여 작업을 본 뒤 조정한다. 연말 완료 보장은 하지 않는다.

## 3. 보유 장비로 진행할 시험 순서

각 행은 작은 연결 시험이다. 데이터 저장·우선순위의 선행 계약/수정이 필요한 경우
해당 WBS 완료 후 실행한다. 실제 장치 작동은 현장 시험 범위가 정해진 뒤 진행한다.

| 시험 ID | 단계·WBS | 첫 시험 범위 | 기록할 증거 | 준비 상태 |
|---|---|---|---|---|
| S01 | 저장·관제 / P2.1~P2.4 | 모형 영상/센서 이벤트 → 영속 저장 → 시험 관제 소비자 | 접수/DB/수신 ID, 저장 실패·복구, 중복·누락, 지연 | P2.3 로컬 완료. Windows 노트북 환경 확인, 원격 수신/ACK·연결 시험 준비. 실제 관제와 구분 |
| S02 | 전광판 / P3.4 | 고정 이벤트 1건 → EdgeX → 실제 화면 → 결과/관제 | event/command/request/device ID, 화면 확인, 실패·복구 | 장비 보유, 과거 DB UAT 있음 |
| S03 | 스피커 / P3.5 | 고정 이벤트 1건 → EdgeX → 실제 음성 → 결과/관제 | 실제 음성, 중복·중단·timeout·복구, ID 대조 | 장비 보유, 현재 연결·실물 검증 필요 |
| S04 | 센서 / P4.1~P4.3 | 온습도부터 확인 후 기울기, 값 변화 → 규칙 → 장치/관제 | 실측값·단위·패킷·시각, 경계/복귀/재접속, 동일 ID 흐름 | 장비 보유, 수/주기·규격 확인 필요 |
| S05 | 영상 / P5.1~P5.5 | CCTV 1대, 낙상→헬멧→의상→색상 각각 평가 | 모델별 정답·오탐/미탐·품질 부족·완료 FPS·지연 | 1대 설정 있음, 운영 반영 범위 확인 필요 |
| S06 | 동시 이벤트 / P6.1 | 영상+센서, 전광판+스피커, 고/저 우선순위와 장치 실패 | 실행 순서, 후순위 DB/관제 보존, 한 장치 장애 격리 | 앞선 모듈·공통 정책 완료 후 |
| S07 | 부하 / P6.2 | 전체 AI 1대→가능하면 실물 2대, 격리 재생 2/4채널 별도 | 카메라별 실제 전체 모델 완료·적체·지연, 조건별 구분 | 실물 2대 연결 가능일·시험 범위 미정 |
| S08 | 최종 실물 / P3.6/P7 | 사이렌 실물 및 총 4카메라 최종 확인 | 실제 작동/정지, 전체 입력·출력·관제, 현장팀 판정 | 사이렌·추가 카메라 확보 대기 |

보유 1~2카메라 시험은 개발·제한된 현장 관찰 범위다. R09의 **실물 4대·전체 운영
AI·매 프레임 30FPS**와 사이렌 실물 요구는 그대로 유지한다. 장비가 없다는 이유로
요구사항을 자동 삭제하거나 재생/모형 결과로 최종 완료하지 않는다.

### 3.1 모듈별 실장비 적용 시점

**전체 개발 종료까지 실장비 시험을 미루지 않는다.** 모듈의 로컬 검증이 끝나면
필요한 선행 조건을 확인하고 아래 단계로 진행한다. P7의 현장팀 POC는 그 결과를
통합해 검증하는 별도 단계다. WBS 목표 주간은 해당 모듈의 통합 완료 목표이며,
읽기 전용 상태 확인이나 준비된 장치의 기초 점검을 그때까지 금지하는 날짜가 아니다.

| 순서 | 적용 범위 | 다음 단계로 넘어갈 근거 |
|---|---|---|
| 1. 로컬 모듈 검증 | 합성/저장 입력·임시 DB·모형 출력으로 계약과 오류/복구 확인 | 해당 변경의 테스트·미해결 이슈·영향 파일 기록 |
| 2. 실제 수신 읽기 확인 | 현재 CCTV/센서의 기존 로그·저장 기록·버전을 확인하고 원본과 공통 값 대조 | 실제 입력 시각·단위·ID·저장 흐름, 로컬 코드와 실행 코드 차이 |
| 3. 한 서비스 적용 | 적용 파일/이미지·이전 사본/백업·복구 명령·중단 범위를 준비하고 유지보수 범위 확인 | 실행 버전과 새 형식의 수신/저장 증거; 실패 시 복구 결과 |
| 4. 한 장치 시험 | 전광판부터 고정 이벤트 1건, 이후 스피커. 대상·중단 방법·현장 확인자 확정 | 명령/응답/DB ID와 실제 화면·음성 확인. ACK만으로 실물 합격 처리하지 않음 |
| 5. 모듈 연결·현장 POC | 영상/센서→저장→우선순위→각 장치/관제, 이후 동시 이벤트·부하 | 앞선 WBS 완료 조건 및 현장팀 POC 판정 |

09-18 현재 새 공통 관측·검증 코드는 **1단계의 로컬 검증 완료 범위**다. 이번 작업에서
서비스 재시작·출력 명령·GPU 시험을 실행하지 않았다. 기존 시스템의 과거 실장비
시험 성과와 새 코드의 적용 여부를 구분한다. 먼저 2단계로 실제 흐름을 대조하고,
운영 동작이 바뀌는 3/4단계는 구체적인 적용/복구 자료를 준비한 뒤 진행한다.

모든 로컬 변경을 한 번에 재시작해 반영하지 않는다. bind mount 소스와 이미지 소스의
반영 방법이 다르고 미커밋 변경이 많으므로 적용 대상만 따로 확인한다. 관제 선정
대기 중에는 내부 수신/저장을 검증하되 실제 관제 수신·표시 합격으로 보고하지 않는다.
