근거 있는 가설**, 카메라 단절·하드웨어 고장·최초 CUDA 원인 확정은 아니다.

### NVDEC/NVENC 오류의 순서

### C++ 전환 검토와 네이티브 시험

[NVIDIA 코덱 문서](https://docs.nvidia.com/metropolis/deepstream/7.1/text/DS_plugin_gst-nvvideo4linux2.html)의

### 이번 수정 — 내부 후처리 통계를 외부 지표에 연결

기존 `get_stats()`에는 후처리 큐 폐기가 있지만 `/metrics`에는 해당 필드가 없었다.
따라서 `frames_dropped=0`만 수집하면 후처리 누락을 놓칠 수 있었다.
`src/services/processor_metrics.py`에 후처리 경계 counter6개를 추가했다.
기존 지표 이름·큐 정책·모델 호출·API 응답·DB 스키마는 변경하지 않았다.
`/metrics`에 이름이 추가되는 변경이며 운영 프로세스에는 아직 반영하지 않았다.

- `context_identity_rejected`: 잘못된 식별자 거부.
- `context_match_expired`: preview 매칭 전 metadata 대기 만료.
- `context_match_evicted`: 대기 metadata 상한에 따른 폐기.
- `context_match_missed`: 일치하는 대기 metadata가 없는 preview.
- `context_frames_matched`: 일치 후 워커 큐 접수, 모델 완료 수가 아님.
- `context_queue_dropped`: 일치한 후처리 작업의 워커 큐 포화 폐기.

Prometheus 이름은 각각 `cctv_processor_<위 필드>_total`, 유형은 counter이며
카메라/인물 라벨은 추가하지 않는다. 계측 필드가 없는 백엔드에서는 가짜0을 만들지 않고 생략한다.
이 지표들을 합해 고유 누락 영상 수로 해석하거나 저장된 이벤트/DB 손실 수로 해석하면 안 된다.
CPU preview 제한과 metadata 대기 매칭은 별도 경계다.

실제 큐2칸에3개의 일치 작업을 넣는 회귀 테스트에서 수정 전 matched 지표가 없어 실패했고,
수정 후 접수2·큐 폐기1·기존 frames_dropped0이 각각 노출됐다. 관련 회귀 **213 PASS/2 SKIP**,
변경 파일 Ruff·diff 검사 통과. 격리 실제 영상에서도 새 지표6개와 **큐 폐기5건**을 확인했다.
RC2 소스357개는 해시 재확인, 계측 보완 파일은 별도 보존하며 기존 RC2를 덮어쓰지 않았다.
네 수신 파일의 상세 프레임 수·시간 순서·디코드 결과는 JSON 근거에 기록한다.

**완료 범위는 후처리 누락의 외부 계측이다.** 큐 포화 해결·CUDA 시작 오류 해결·운영 적용·
전체 모델30fps·다중 입력 합격은 아니다. I32/I34/I07 OPEN·P5.1 IN_PROGRESS 유지.
운영 AI는 healthy·시작 시각 유지·Docker restart0이며 실제 출력 장치 명령은 보내지 않았다.

### 수정 — Jetson 영상 버퍼 복사를 VIC로 선택

[NVIDIA DeepStream 7.1 문제 해결 문서](https://docs.nvidia.com/metropolis/deepstream/7.1/text/DS_troubleshooting.html)는
Jetson의 `Failed in mem copy`/오류700 계열에 surface-array를 VIC로 복사하는 `copy-hw=2`를 안내한다.
증상에 맞는 공식 우회책이지만 원 실패 위치를 직접 입증한 결과는 아니다.

- `src/core/deepstream_processor.py`: 영상 변환기 생성 시 `DS_NVVIDEOCONVERT_COPY_HW`를 적용한다.
  빈 값은 SDK 기본, `1`은 GPU, `2`는 VIC다. 잘못된 값은 즉시 실패하며 지원하지 않는 속성을
  조용히 무시하지 않는다. 다른 종류의 GStreamer 요소는 영향받지 않는다.
- `docker-compose.jetson.yml`: 위 환경 키를 기본 빈 값으로 전달한다.
  운영 `.env.jetson` 변경이나 컨테이너 재생성은 하지 않았다.
- `tests/test_deepstream_processor.py`: 기본/명시 선택·잘못된 값·다른 요소 영향 없음의8조건.
  수정 전6실패/2통과, 수정 후 관련 회귀 **248 PASS / 2 SKIP**, 변경 코드 Ruff 통과.
- [배포 환경 변수 안내](../guides/DEPLOYMENT_ENVIRONMENT_VARIABLES.md)에 적용 범위·제약을 기록했다.

기존 GPU 모델 추론, nvinfer scaling-compute-hw, DB 스키마, 이벤트 계약은 바꾸지 않았다.
RC3는 RC2에 v0.61 지표 collector와 이번 복사 선택 코드2개 파일을 교체한 후보이며
357개 소스/설정 해시와 보존 archive 해시를 재확인했다. 기존8개 모델 보존본을 그대로 참조한다.

dGPU나 CUDA device/unified 메모리 조합의 호환성을 주장하지 않는다.

### 확정 수정 — 치명적 오류 이후 같은 프로세스 재사용 차단

기존 bus 처리와 실행 루프는 치명적 오류를 소스 재연결 또는 같은 프로세스의 stop/start로
보낼 수 있었다. [CUDA Runtime 공식 문서](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__TYPES.html)의
`cudaErrorIllegalAddress`는 프로세스가 일관되지 않은 상태가 되어 종료/재실행이 필요한 오류다.

- `_deepstream_source_health.py`: 명시적 `cudaErrorIllegalAddress`/`NVDSINFER_CUDA_ERROR`를
  치명적 오류로 구분한다. 원 장애의 bus 메시지처럼 SDK `gst_nvinfer_input_queue_loop`의
  `Failed to queue input batch for inferencing`도 프로세스 재실행 대상으로 취급한다.
  후자는 CUDA700 확정 판정이 아니라 별도의 `inference_queue_failure` 사유다.
- `deepstream_processor.py`: 최초 치명적 사유를 유지하고 동일 인스턴스의 start를 거부한다.
- `bootstrap/runtime.py`: 정리 후 종료 코드1로 외부 감독자에게 알린다. 일반 입력 오류는
  기존 재시도를 유지한다. 직접 CLI 실행 시 새 프로세스 시작은 실행자/감독자 책임이다.
- `tests/test_deepstream_fatal_error.py`: 수정 전4실패/1통과, 수정 후 인접 회귀255 PASS/2 SKIP.
  정상 소스 재시도와 치명적 종료를 따로 검사했다. 변경 코드 Ruff/diff 검사 통과.

RC4 실제 CLI에서100프레임 이상 처리 후 원 장애와 같은 SDK 오류 메시지를 실제 GStreamer
bus에 게시했다. 앱이 종료 코드1로 끝나고 같은 프로세스의 start 반복이 없는지 확인했다.
이는 **합성 bus 오류 주입**이며 실제 GPU 불법 접근을 새로 발생시킨 시험은 아니다.
