# 상·하의 색상 검수 및 재학습 데이터 내보내기 설계

## 목적

운영 중 저장된 사람 crop을 로컬 HTML에서 사람이 검수하고, 상의와 하의 색상을 각각 정정할 수 있게 한다. 검수 결과는 기존 `appearance_log` 기록에 안전하게 반영할 수 있고, 추후 모델 재학습에 사용할 원본 라벨 데이터로 별도 보존한다.

검수 직후 자동 재학습하거나 모델을 자동 배포하지 않는다. 라벨 수량과 품질을 확인하고 오프라인 평가를 통과한 모델만 Jetson/DeepStream에 배포한다.

## 현재 상태와 제약

- `build_appearance_color_review_manifest.py`는 상의와 하의 후보를 모두 수집할 수 있다.
- `build_appearance_review_html.py`는 현재 하의(`lower_color`)만 표시하고 하나의 `review_label`만 다운로드한다.
- `import_appearance_color_review_labels.py`는 단일 색상 분류 디렉터리를 만들며 DB를 갱신하지 않는다.
- 로컬 HTML은 웹서버 없이 `file://`로 실행되므로 브라우저에서 SQLite DB를 직접 수정할 수 없다.
- 기존 multi-label 학습 목록은 9개 색상을 지원하지만 런타임 색상 판정은 `orange`, `pink`를 포함한 11개 색상을 사용할 수 있다. 이 차이를 숨기거나 자동 변환하지 않는다.

## 채택한 접근

현재 로컬 HTML 방식을 유지하면서 역할을 세 부분으로 분리한다.

1. 검수 HTML은 상의와 하의의 저장값 및 후보값을 보여주고, 각 필드의 정답을 독립적으로 선택하게 한다.
2. DB 적용 스크립트는 검수 JSON을 검증하고 미리보기를 제공한 뒤, 명시적인 적용 옵션이 있을 때만 `appearance_log`를 갱신한다.
3. 학습 데이터 내보내기 스크립트는 검수 JSON과 원본 manifest를 결합해 재현 가능한 검수 라벨 manifest와 요약 보고서를 생성한다.

별도 검수 웹 API 서버는 추가하지 않는다. 현재 요구사항에 비해 운영·인증·장애 복구 비용이 크기 때문이다.

## 검수 화면

각 행은 다음 정보를 표시한다.

- ID와 crop 이미지
- 현재 DB 상의/하의 색상
- 상의 HSV/LAB/model 후보
- 하의 HSV/LAB/model 후보
- 상의 정답 드롭다운
- 하의 정답 드롭다운

두 드롭다운의 초기값은 `변경 안 함`이다. 사용자는 한 필드만 정정하거나 두 필드를 모두 정정할 수 있다. 선택하지 않은 필드는 DB에서 변경하지 않는다.

DB에 저장 가능한 색상은 다음 11개로 제한한다.

`black`, `blue`, `brown`, `gray`, `green`, `orange`, `pink`, `purple`, `red`, `white`, `yellow`

`exclude`는 해당 crop을 학습 데이터에서 제외한다는 검수 상태이며 DB 색상값으로 저장하지 않는다.

## 검수 JSON 형식

다운로드 파일명은 `appearance_color_review_labels.json`으로 한다.

```json
{
  "schema_version": 1,
  "items": [
    {
      "id": 323388,
      "upper_color": "white",
      "lower_color": "gray"
    },
    {
      "id": 323389,
      "upper_color": null,
      "lower_color": "exclude"
    }
  ]
}
```

`null`은 변경하지 않음을 의미한다. `exclude`는 해당 필드의 DB 값을 변경하지 않고 학습 내보내기에서 제외한다. 동일 ID가 중복되거나 알 수 없는 색상값이 들어오면 입력 전체를 거부한다.

## DB 반영

새 DB 적용 스크립트는 `--db`와 `--labels`를 입력받는다.

- 기본 실행은 dry-run이며 변경 전/후 값과 변경 건수를 출력한다.
- `--apply`가 있을 때만 실제 DB를 수정한다.
- 적용 전 원본 DB 옆에 시각이 포함된 백업 파일을 만든다.
- 모든 ID와 라벨을 먼저 검증한다.
- 존재하지 않는 ID나 잘못된 라벨이 하나라도 있으면 아무 행도 수정하지 않는다.
- 유효한 변경은 하나의 SQLite 트랜잭션으로 적용한다.
- `null`, `exclude`, 현재 DB 값과 동일한 선택은 수정 건수에서 제외한다.

이 작업은 과거 검색 결과의 색상값을 정정하지만 실행 중인 모델의 추론 방식에는 영향을 주지 않는다.

## 학습 데이터 내보내기

검수 결과는 DB 적용 여부와 무관하게 원본 manifest와 결합하여 별도 디렉터리에 보존한다.

산출물은 다음과 같다.

- `reviewed_appearance_colors.csv`: `image_path`, `appearance_log_id`, `upper_color`, `lower_color`, 각 필드의 검수 여부
- `reviewed_appearance_colors.json`: 원본 후보값과 사람 정답을 포함한 감사용 데이터
- `summary.json`: 색상별 수량, 부분 검수 수량, 제외 수량, 학습 파이프라인 미지원 색상 수량

사람이 선택하지 않은 필드에 기존 DB 값을 자동으로 정답으로 채우지 않는다. 그렇게 하면 오판정이 다시 학습 데이터에 들어갈 수 있기 때문이다.

현재 multi-label 학습기는 부분 라벨 마스크를 지원하지 않고 색상 집합도 런타임과 다르다. 따라서 이번 단계의 산출물은 **검증된 라벨 원본 데이터셋**이며 기존 학습 목록 생성기에 무조건 연결하지 않는다. 실제 재학습 단계에서는 다음 중 하나를 명시적으로 선택해야 한다.

- 상의와 하의가 모두 검수되고 학습기가 지원하는 9개 색상에 속한 행만 기존 multi-label 학습에 사용
- 부분 라벨과 11개 색상을 지원하도록 모델 출력/손실/라벨 맵을 별도 변경

두 번째 선택지는 모델 출력 차원과 TensorRT/DeepStream 배포 설정에 영향을 주므로 이번 변경 범위에서 제외한다.

## 오류 처리와 운영 안전성

- crop 파일이 없으면 HTML 생성 및 학습 내보내기 요약에 오류 사유를 기록하고 해당 항목을 건너뛴다.
- JSON 스키마 오류, 중복 ID, 허용되지 않은 값은 즉시 실패시킨다.
- DB 적용은 일부 성공을 허용하지 않는다.
- 백업 생성에 실패하면 DB 적용을 시작하지 않는다.
- 브라우저를 닫기 전에 JSON 다운로드가 필요하다는 안내를 화면에 표시한다.

## 테스트 전략

- HTML에 상의·하의 후보와 독립적인 두 드롭다운이 생성되는지 확인한다.
- 다운로드 JSON이 `schema_version`, ID, 상의/하의 값을 올바르게 포함하는지 확인한다.
- 한 필드만 선택한 부분 수정이 다른 필드를 유지하는지 확인한다.
- dry-run이 DB를 변경하지 않는지 확인한다.
- `--apply`가 백업을 만들고 유효한 행만 한 트랜잭션으로 수정하는지 확인한다.
- 중복 ID, 없는 ID, 잘못된 색상, 백업 실패 시 전체 적용이 중단되는지 확인한다.
- 학습 데이터 내보내기가 미검수값을 정답으로 채우지 않고 `exclude`와 누락 crop을 집계하는지 확인한다.
- 기존 appearance 관련 테스트를 함께 실행해 회귀 여부를 확인한다.

## 완료 조건

- 한 HTML 행에서 상의와 하의 색상을 독립적으로 지정할 수 있다.
- JSON만 다운로드한 상태에서는 DB가 바뀌지 않는다.
- 사용자가 dry-run 결과를 확인한 뒤 명시적으로 적용할 수 있다.
- DB 적용 전 복구 가능한 백업이 생성된다.
- 검수 결과가 재학습 준비용 CSV/JSON과 요약으로 재현 가능하게 저장된다.
- 모델 재학습 및 운영 배포는 자동 실행되지 않는다.
