# Jetson Pose 1080p·720p 실제 입력 비교 — 2026-09-17

## 결론

**현재 후보에서 720p 입력만으로 4채널 × 30FPS를 확보하지 못했다. 운영 변경 없음.**
입력 파일과 mux 크기를 함께 줄였지만, 4채널 3회 반복은 채널별 평균 13.16FPS였다.
같은 인코딩 조건의 1080p 대조군은 13.93FPS였다. 공유 부하가 통제되지 않았으므로
이 차이를 해상도 하향의 역효과나 인과적 성능 차이로 단정하지 않는다.
두 구성 모두 측정 중 재생 지연이 크게 누적됐다.

| 추가 재생 구성 | 채널별 FPS | 측정 시간 | 측정 중 지연 증가 |
| --- | --- | --- | --- |
| 720p 1채널 | 30.0065 | 20.029초 | +0.0063초 |
| 720p 2채널 | 각 22.9704 | 30.039초 | 각 +7.0005초 |
| 720p 4채널, 3회 | 13.6476 / 12.9167 / 12.9167 | 회당 약 30.04초 | +16.37 / 17.16 / 17.09초 |
| 1080p 4채널, 3회 | 13.6152 / 13.5816 / 14.5812 | 회당 약 30.04초 | +16.36 / 16.48 / 15.37초 |
| 원본 1080p 4채널, 사후 대조 | 각 13.5152 | 30.040초 | +16.5066~16.5076초 |

4채널 반복 행의 FPS는 매 실행의 최소 채널 FPS다. 이번 여섯 실행에서는 각 실행의
네 채널 FPS가 모두 같았다. 시험 전후 운영 카메라 1대와 다른 서비스는 유지됐다.
따라서 **추가 4개 재생 입력 + 기존 운영 입력의 공존 부하**이며, 전용 환경의
실물 카메라 4대 용량이나 모든 운영 AI의 합격 판정이 아니다.

## 이전 20.14FPS 결과와의 차이

[앞선 L1 후보 시험](JETSON_POSE_OPTIMIZED_BUILD_20260917.md)은 원본 입력에서
4채널 각각 20.1409FPS였다. 이번 재인코딩 비교가 더 느려 원본 파일을 그대로
사용한 사후 대조 실행을 추가했다. 같은 엔진·시험 도구·원본 해시를 유지했는데도
현재 시점에서는 13.5152FPS였다.

따라서 이번 하락을 720p 변환이나 코드 변경만의 효과로 설명할 근거는 없다.
공유 GPU/CPU 부하와 클럭 등 실행 조건의 영향이 의심되지만, 원인별 기여는
미분리 상태다. 이전 단회 값을 고정 성능 보장으로 사용하거나 이번 값만으로
Jetson 하드웨어의 절대 한계를 확정하지 않는다. 원본 대조는 사후 단회 진단이며
미리 계획한 해상도별 3회 평균에 섞지 않았다.

`tegrastats_original_control.log`는 원본 대조 실행 중 15:48:26~59 KST 표본이다.
해당 컨테이너의 plugin 시작 로그는 15:48:20, 결과 파일 작성은 15:49:03이다.
GPU GR3D 사용률은 표본에서 97~98%였다. 장치 전체 사용률이므로 시험 모델에만
귀속하지 않는다. 이 감시 명령은 지정한 35초 제한의 종료 코드 124로 끝났으며,
부하 시험 실패나 OOM이 아니다. 실제 원본 대조 시험은 종료 코드 0이다.

## 입력 생성과 전체 프레임 시각 검증

결과 루트: `data/benchmarks/pose_resolution_20260917.Hgx7sU/`.

`a04810f2619bcf939386491ef66b41acc4e230a264bf839497d0164d63d197ab`.
ffprobe 메타데이터의 `nb_frames`는 3598이지만, 이번 FFmpeg 4.4.2의 전체 디코딩
`show_frames` 결과는 **3597개**였다. 메타데이터 수를 실제 디코딩 수와 혼동하지 않는다.
원본 시각은 모두 증가했고 첫 두 프레임은 0과 1/90000초, 마지막은 119.94초였다.
이 차이의 컨테이너/디코더 원인을 확정하거나, 다른 하드웨어 디코더의 프레임 수까지
같다고 주장하지 않는다.

첫 720p 변환은 기본 encoder time base에서 가까운 두 시각이 겹쳐
non-monotonic PTS/DTS 경고가 발생했다. `replay_720p.mp4`와 로그는 보존하되
성능 비교에서 제외했다. 짧은 1초 진단에서 `-enc_time_base -1`로 원본 시간
단위를 유지하는 설정을 검증한 뒤, 1080p와 720p 파일을 같은 조건으로 생성했다.
인코딩 프로그램의 설치된 도움말에서 -1의 의미를 직접 확인했다.

공통 생성 조건:

```text
FFmpeg 4.4.2 / libx264
-preset veryfast -crf 18 -profile:v main -pix_fmt yuv420p -threads 2
-enc_time_base -1 -video_track_timescale 90000 -vsync 0 -movflags +faststart
scale=<1920:1080 또는 1280:720>:flags=lanczos:in_range=pc:out_range=tv
```

CPU nice 10, 인코더별 2 thread, filter threads 2, timeout 900초, `-n`으로 기존 파일
덮어쓰기 금지. 원본에서 비디오만 각 출력에 매핑했고 오디오/자막/데이터는 제외했다.

## 반복 통계와 시각 지표의 제한

4채널 실행 순서: 720→1080→720→1080→720→1080. 두 초기 sanity 실행 이후
warmup 10초, 측정 30초로 통일했다. 합산 FPS로 느린 채널을 숨기지 않고
각 실행의 최소 채널 FPS를 분석 단위로 사용했다.

| 입력 | 실행 단위 평균 FPS | 실행 간 표준편차 | 참고용 95% t 구간 |
| --- | --- | --- | --- |
| 720p | 13.1603 | 0.4220 | 12.1121~14.2085 |
| 1080p | 13.9260 | 0.5677 | 12.5158~15.3362 |

`mean ± t(0.975, df=2) × sample_sd / sqrt(3)`로 계산했다. 4채널×3회를 독립
12회로 부풀리지 않았다. 공유 부하·시점 효과·작은 표본 때문에 독립성/정규성을
보장하지 못하므로 구간은 편차를 기술하는 참고치이며, SLA의 95% 보장이 아니다.
구간이 겹친다는 사실만으로 통계적 동등성이나 특정 가설의 검정을 주장하지 않는다.

지연은 같은 실행 안의 `clock - base_time - buf_pts` 변화다. 720p 1채널에서는
원시 시작/끝 값에 약 -12~-5ms의 작은 음수가 관측됐다. SEGMENT/시각 offset 등을
일반적으로 보정하는 계측이 아니므로 이 절대값을 실제 촬영~AI 지연으로 해석하지 않는다.
고정 파일·seek/loop 없는 이번 실행에서 영상 시간 대비 처리 적체의 **증가량**만
진단에 사용하며, `last_frame_age_seconds`와도 구분한다.
