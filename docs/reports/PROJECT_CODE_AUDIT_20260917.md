# CCTV 프로젝트 코드·운영 구조 분석 및 리팩토링 우선순위

분석일: 2026-09-17 · 범위: 현재 로컬 작업 트리와 실행 중인 Jetson 구성

## 1. 결론

**전면 재작성보다, 장치 제어의 안전성과 상태 신뢰도를 먼저 고치는 단계적 리팩토링이 필요하다.**

API·AI·장치 드라이버·EdgeX 서비스의 기본 분리는 이미 있고 테스트도 상당하다. 그러나 “EdgeX 설정을 켰다”, “명령 발행에 성공했다”, “컨테이너가 healthy다”를 각각 “모든 제어가 EdgeX를 거친다”, “장비가 동작했다”, “업무 흐름이 정상이다”로 해석할 수 없는 경로가 남아 있다.

이번 분석에서는 운영 코드 변경, 서비스 재시작, 장비 작동, 파일 삭제를 수행하지 않았다. 이 문서만 추가했다. 기존 수정·스테이징·미추적 파일은 보존했다. 아래 작업은 **수정 제안이며 구현 완료 목록이 아니다.**

## 2. 조사 범위와 검증 수준

- 코드 그래프의 구조·호출 관계를 먼저 확인하고, 핵심 경로 소스와 설정을 대조했다. 그래프가 부족하거나 혼재된 부분은 실제 파일을 확인했다.
- `src`, `runners`, `app`, `parser-python`, `scripts`, `tests`, `web`의 Git 추적 파일 576개 중 Python 파일은 544개다. 전체 구조와 주요 위험 경로를 검토했으며, 모든 행의 완전 검증을 뜻하지 않는다.
- 시작 시 이미 추적 파일 약 205개가 변경/추가 상태였다. 이번 결과는 HEAD만이 아니라 해당 작업 트리를 포함한다.
- Docker 상태·마운트·포트를 읽기 전용으로 확인했다. 전광판 컨테이너의 서비스/실행기/드라이버 3개 파일은 로컬 파일과 SHA-256이 같았다. 모든 이미지의 일치 여부까지 확인한 것은 아니다.
- 가짜 장비와 임시 SQLite DB로 대상 라우팅·중복 처리·성공 판정·배치 유실을 재현했다. 실제 장비에 테스트 명령을 보내지 않았다.
- 전체 테스트, 제한된 소스 범위 Ruff, 기존 배포 점검 스크립트를 실행했다.
- GPU 성능/모델 정확도 재평가, 브라우저 현상 재현, 실제 스피커·사이렌 UAT, 재부팅 UAT, 새 이미지 빌드, 온라인 취약점 조사는 미실시다.

### 현재 구조에서 유지할 부분

`src/api`, `src/core`, `src/services`, `src/edgex`, `src/devices` 구분, 이벤트/명령 식별자, 기존 HTTP/MQTT outbox, 모델 평가 도구, 장면 단위 데이터 분할, SQLite 연결 정리, 운영 정리 스크립트 등은 유지·확장하는 것이 현실적이다. 새 마이크로서비스 체계나 프런트엔드 프레임워크 도입이 선행 조건은 아니다.

## 3. 상세 발견 사항

### P0-1. 내부 장비 제어 API 노출

**확인:** `runners/run_signboard_device_service.py`의 `_CommandHandler._handle_command`와 스피커·사이렌 및 구형 Dabit 실행기의 제어 핸들러에 호출자 인증 검사가 없다. Jetson Compose와 실제 컨테이너의 59990~59993 포트 바인딩에 호스트 IP 제한이 없다. 요청 본문 크기 제한도 보강해야 한다.

**영향:** 해당 호스트 포트에 접근 가능한 주체가 공개 API 인증 경로를 거치지 않고 장비 제어를 시도할 수 있다. 인터넷에서 접근 가능한지는 방화벽·라우터 확인 전에는 단정할 수 없다.

**수정:** 컨테이너 내부 통신만 필요한 포트는 publish 제거, 유지보수용은 loopback/관리망 제한. 서비스 간 인증과 허용 동작·본문 크기 검증을 추가한다. EdgeX 호출 계약을 함께 갱신해야 하므로 배포 영향이 있다.

**완료 기준:** 무인증/잘못된 인증 요청 거부, 외부 인터페이스 접근 차단, 승인된 EdgeX 요청 정상 처리. `check_internal_port_exposure.py`에도 Device Service 포트를 포함한다.

### P0-2. 환경 백업과 비밀값 검사 사각지대

**확인:** `.env.jetson.backup_1080p_before_20260911`, `.env.jetson.backup_20260911`, `.env.jetson.backup_fps_before_20260911`, `.env.jetson.backup_pose_before_crop_20260911`은 미추적이며 ignore되지 않는다. API 키/암호/내부 토큰에 해당하는 비어 있지 않은 항목을 확인했다. 실제 값은 기록하지 않는다.

`.gitignore`는 정확한 환경 파일명 중심이고 `.dockerignore`도 관련 백업을 포괄하지 못한다. `check_sensitive_defaults.py`의 점검 대상은 일부 예제·Compose 파일로 제한된다. Dockerfile의 COPY가 명시적이므로 **백업이 이미지에 들어갔다고 단정할 수는 없다.**

**수정:** 백업을 삭제하기 전에 롤백 용도와 보관 위치를 정리하고 접근 권한을 제한한다. 환경 백업 패턴을 Git/빌드 컨텍스트에서 제외하고 예제 파일은 명시적으로 유지한다. 비밀값 검사 범위를 넓힌다. 이미 공유·커밋됐는지 별도 확인 후 필요하면 키를 교체한다.

### P1-1. EdgeX 모드에도 직접 제어 경로와 중복 제어 주체가 남음

**확인:** `src/services/action_bridge.py` 생성자는 EdgeX 모드에서도 `SpeakerDevice`, `SignboardDevice`, `SirenDevice`를 생성한다. `src/devices/signboard.py`는 호스트가 설정되면 idle 스레드를 시작하고 직접 TCP로 시간표시를 전송하는 경로가 있다. 모의 생성 테스트에서도 EdgeX 모드의 직접 idle 스레드 시작 호출이 1회 발생했다.

실행 중인 서비스에도 구형 `cctv-device-dabit`과 신형 `cctv-device-signboard`가 함께 존재한다. 따라서 Action Layer까지 포함해 동일 전광판을 제어할 주체가 중복될 수 있다. 실제 화면 덮어쓰기는 이번에 현장 재현하지 않았다.

**수정:** EdgeX 운영 모드의 Action Layer는 명령 생성·발행·결과 추적만 맡긴다. 저수준 드라이버와 시간표시는 단일 Device Service가 소유한다. 구형 서비스는 등록 정보·호출자를 확인한 뒤 별도 legacy profile로 격리하고 전환 검증 후 제거한다.

**완료 기준:** EdgeX Action Layer에서 장비 소켓 연결/idle 스레드가 생성되지 않음, 장비당 제어 서비스 1개, 재부팅 후에도 동일. 저수준 드라이버 자체는 삭제하지 않는다.

**기존 설명 정정:** 환경변수만으로 “모든 장치가 즉시 EdgeX로 전송된다”는 보장은 성립하지 않는다. 또한 allowlist에서 빠진 장치를 자동 Direct fallback으로 간주해서도 안 된다. 현재 resolver는 허용되지 않은 장치를 제외한다.

### P1-2. HTTP 대상 장치와 중복 요청 계약 결함

**확인:** `src/edgex/command_http.py:handle_command_request`는 URL의 장치 ID가 등록됐는지 확인하지만 실행 요청에 `device_id`를 넣지 않는다. 서비스는 기본 장치로 처리할 수 있다. 모의 테스트에서 `board-2` 요청이 `board-1`에서 실행됐다.

동일 경로의 기본 요청 ID `edgex-command`는 서로 다른 명령에도 반복 사용된다. 성공 결과 캐시 때문에 두 개의 다른 요청 중 한 개만 장비 호출로 이어지는 상황을 재현했다.

`src/edgex/request_idempotency.py`는 조회와 저장 각각을 잠그지만, Device Service의 조회→실행→저장 전체는 원자적이지 않다. 동시에 들어온 동일 ID 요청 2개가 물리 호출 2회로 이어졌다. 캐시는 메모리이므로 재시작 후 중복 방지도 유지되지 않는다.

**수정:** 검증한 대상 ID를 실행 요청에 명시한다. 요청 ID를 경계에서 필수로 받거나 새로 생성하고, `(device_id, request_id)`와 명령 내용의 일치를 검증한다. 진행 중 예약을 원자적으로 처리하고 결과·만료시간을 필요한 범위에서 영속화한다. 외부 장비까지 무조건 exactly-once라고 보장하지 말고 불확실한 실행 결과를 구분한다.

**완료 기준:** 다중 장치 중 정확한 대상만 실행, 다른 요청은 각각 실행, 동일 요청의 동시 재전송은 1회 실행, 같은 ID에 다른 본문은 거부, 재시작/타임아웃 정책 테스트 통과.

### P1-3. 발행 성공과 장비 성공 혼동, 다중 장치 실패 가림

**확인:** `src/services/device_command_transport.py:EdgeXCommandTransport.send`는 발행 콜백이 true면 장비 결과 없이 `acknowledged`를 반환한다. Action Layer의 발행 성공 판단도 MQTT 로컬 발행 반환값 중심이다. `_action_bridge_executor.py`의 성공·알람 재생 상태가 이 결과에 의존한다.

`src/services/edgex_result_handler.py`는 물리 장치별 요청 ID를 논리 명령 ID로 합쳐 저장한다. `_action_bridge_repo.py`의 upsert는 마지막 결과로 상태를 갱신한다. 한 장치 실패 뒤 다른 장치 성공을 입력하자 논리 명령 한 행이 성공으로 남았다. 별도의 원시 결과 저장소까지 모든 실패 정보가 사라진다는 뜻은 아니다.

**수정:** `queued/published/executing/acknowledged/failed/timeout`을 구분하고 장치별 결과와 논리 명령 집계를 분리한다. 부분 실패와 늦게 도착한 결과 처리 규칙을 정한다. 명령 outbox와 결과 제한시간을 두되, 오래된 경보가 복구 후 재생되지 않도록 TTL·취소 정책을 함께 둔다. DB/API 계약 변경이 필요하다.

**완료 기준:** 발행만으로 UI가 실제 실행 완료를 표시하지 않음, 하나라도 실패한 다중 장치 작업은 전체 성공으로 표시되지 않음, 연결 단절·결과 누락·순서 역전 테스트 통과.

### P1-4. 직접 연결 확인과 동기 실행이 EdgeX 전송을 지연·제외

**확인:** `action_bridge.py:_device_is_available`는 EdgeX 모드와 무관하게 직접 연결 설정과 스피커·사이렌 TCP 도달성을 확인한다. resolver에서 이를 사용한다. 모의 테스트에서 EdgeX 모드인데도 직접 TCP 확인 후 대상을 제외했다. 연결 실패 타임아웃과 약 30초 캐시가 명령 대상·응답시간에 영향을 줄 수 있다.

Device Service 실행기들의 MQTT 콜백은 실제 장치 실행을 동기 호출한다. 종류별 컨테이너 분리는 있지만 동일 종류의 여러 장치 중 하나가 느린 경우의 격리는 부족하다.

**수정:** EdgeX 모드에서는 등록·활성 정책으로 대상을 선택하고 실행 가능 여부는 담당 서비스가 결과로 보고한다. MQTT 콜백은 검증·대기열 삽입 후 반환하고 제한된 장치별 실행 큐를 사용한다. 큐 상한, 장치별 timeout, 만료·취소·과부하 정책을 명시한다.

**완료 기준:** 오프라인 스피커가 정상 전광판 전송을 막지 않음, 같은 종류의 장치 장애도 나머지에 전파되지 않음. 지연 목표 수치는 현장 요구에 맞춰 정한 뒤 p50/p95/p99로 확인한다.

### P1-5. 센서 배치 유실과 운영 정책의 재시작 복구 부족

**확인 A:** `parser-python/database/processor.py:_process_all_tables`는 대기 배치를 꺼낸 뒤 DB insert에 실패하면 로그만 남기고 해당 배치를 복구하지 않는다. 1건을 넣고 DB 실패 후 두 번 flush한 모의 테스트에서 남은 건수 0, insert 시도 1회였다. 이 결함은 해당 DB 배치 경로이며, 이미 존재하는 별도 EdgeX HTTP outbox까지 없다는 뜻은 아니다. 메모리 대기열의 상한과 종료 시 flush도 보강 대상이다.

**확인 B:** `src/services/_action_bridge_site_registry.py`의 사이트·운영 모드·승인 대기 상태는 메모리에 보관된다. 실행기의 재시작 복구 경로가 부족하여 수동 모드와 대기 승인 상태가 유지되지 않을 수 있다. 과거 UI 문제의 실제 원인이었다고 단정하지 않는다.

**수정:** 센서는 영속 spool/outbox에 적재하고 DB commit 이후 완료 처리한다. 재시도·dead letter·용량 상한·유실 계수를 제공한다. 사이트 운영 모드와 승인 상태는 저장·복구하며 승인/거부 전이와 감사 기록을 함께 처리한다.

**완료 기준:** DB 중단→복구·프로세스 종료→시작 시험에서 보존 정책 충족, 무한 메모리 증가 없음, 수동 모드가 재시작 후 임의로 자동 모드가 되지 않음.

### P1-6. 운영 정책·배포 입력·검사 기준 불일치

**확인:** 현재 환경은 EdgeX 운영인데 `.env.jetson.example`, Compose 기본값, 일부 운영 문서와 검사에는 Direct 기본/롤백 가정이 남아 있다. 전체 테스트의 유일한 실패도 실제 `.env.jetson`을 읽고 기존 Direct 롤백 조건을 요구하는 테스트였다. 운영 설정과 무관한 fixture 기반 테스트로 바꿔야 한다.

Device Service 컨테이너에는 `config/output_devices.json` 마운트가 없고 전광판 컨테이너 안 해당 파일도 없었다. 파일 기반 registry가 적용되지 않으면 환경변수 기반 단일 장치 fallback에 의존한다. 여러 장치 구성 파일을 수정했다고 서비스에 반영되는 구조가 아니다.

**수정:** “모든 장치 EdgeX”를 운영 정책으로 명시하고 예제·문서·검사를 통일한다. 자동 Direct fallback을 새로 추가하지 않는다. 정상 EdgeX 버전으로 돌아가는 롤백을 우선 정의한다. registry를 읽기 전용으로 제공하고 명시한 파일이 없을 때 조용히 넘어가지 않게 한다.

프로세스 생존/HTTP 200과 MQTT 연결·구독·registry 로딩·장치별 통신 상태를 분리한다. 부분 장치 장애를 서비스 전체 무한 재시작으로 처리하지 않도록 liveness와 readiness를 구분한다.

### P2-1. AI 런타임·학습 코드 결합과 모델 검증 사각지대

**확인:** `src/core/ai/_falldata_aux.py`는 특징 계산을 위해 `scripts/datasets/train_yolo_pose_fall_rf.py`의 함수를 import한다. Jetson의 scripts 마운트에 기대는 반면 이미지 자체의 복사 구성은 이를 보장하지 않는다. 개발 폴더 배치가 추론 계약의 일부가 된다.

해당 verifier의 영상 `_frames`는 카메라별 키가 없는 단일 버퍼다. `deepstream_processor.py`의 preview 프레임 전달 및 near-miss 검증 경로와 조합하면 다중 카메라에서 다른 카메라의 프레임으로 검증할 위험이 있다. 카메라 키를 가진 pose 기록 경로까지 모두 혼합된다는 뜻은 아니며 현장 오판 재현은 미실시다.

`scripts/promote_fall_model.py`는 비교 결과의 승격 불리언과 지정한 candidate 경로를 사용하지만 동일 모델 hash를 강하게 결합하지 않는다. 복사도 원자적 교체·롤백 manifest까지 보장하지 않는다.

**수정:** 순수 특징 계산/스키마를 `src/core/ai` 공용 모듈로 옮겨 학습·추론이 함께 사용한다. 카메라별 시간창 버퍼와 이벤트 시각 계약을 정한다. 승격에는 모델 hash·특징 스키마·데이터셋 버전·평가 결과를 묶고 원자적 교체 및 이전 모델 복구를 둔다.

**평가 방향:** 기존 장면 단위 분할·평가 도구는 유지한다. 초반 배회 구간과 실제 낙상 구간을 분리하되, “30초 이후만 잘됨”만으로 운영 합격을 내리지 않는다. 사건 단위 누락, 정상 장시간 오경보, 감지 지연, 카메라별 편차, Jetson FPS/메모리를 함께 본다. 9/16 영상 타임라인 분석 기록은 이미 있으므로 새 평가와 중복하지 말고 그 근거를 이어 쓴다. 이번 분석에서는 candidate의 새 합격 판정을 내리지 않았다.

### P2-2. UI 요청 정지와 API 이벤트 루프 점유 위험

**확인:** `web/public-demo.html`은 3,886행에 화면·스타일·통신·상태 처리가 함께 있다. `refreshAll`의 진행 중 플래그와 `Promise.allSettled`에 비해 공용 요청 함수의 제한시간 처리가 부족하다. 한 요청이 끝나지 않으면 후속 갱신이 계속 무시될 수 있다. 일부 health 요청의 제한시간은 이미 존재한다. 브라우저에서 실제 멈춤을 이번에 재현한 것은 아니다.

`src/api/v1/search.py` 등 async 경로에서 동기 SQLite 조회/초기화를 직접 호출한다. DB 잠금 대기 시 이벤트 루프를 점유할 수 있다. 다른 이벤트 API에 이미 있는 `asyncio.to_thread` 패턴을 참고할 수 있다. 결과 저장소 30회 조회 테스트에서 FD 증가가 없었으므로 FD 누수로 단정하지 않는다.

**수정:** 프레임워크 교체 없이 API 클라이언트·상태·화면별 렌더링부터 나눈다. 공통 AbortController/제한시간과 영역별 오류·마지막 갱신 시각을 표시한다. DB 초기화 수명과 동기 호출 실행 위치를 정리하고 동시 실행 수를 제한한다.

**완료 기준:** 센서/검색 API 한 곳이 느려도 다른 화면·상태 갱신 유지, 취소/재시도/오류 표시 확인, DB 잠금 조건에서 health 응답 지연 측정.

### P1/P2. CI와 자동화의 안전망 부족

- `.github/workflows/ci.yml`의 pytest 대상은 `tests/`여서 `parser-python/tests`가 빠진다. 두 경로를 동일하게 검증해야 한다.
- 이미지 build/push 작업의 `needs`는 `test`뿐이다. `compose-config`와 `security-scan` 성공도 배포용 이미지 발행 조건에 포함해야 한다.
- 타입 검사 설정과 별개로 CI 실행·coverage 기준이 부족하다. 전체 비율만 올리기보다 위에서 재현한 명령/복구 경로를 우선 보호한다.
- `scripts/ops/weekly_git_push.sh`는 일부 경로만 stage하며 `runners/app/parser-python` 등 연관 수정이 빠질 수 있다. 자동 커밋·푸시 전에 테스트/배포 계약을 확인하는 흐름이 필요하다. 실제 타이머 실행이나 정보 유출은 이번에 확인하지 않았고 중지하지도 않았다.
- 의존성 범위와 Jetson 호스트 학습 환경을 재현 가능한 버전·이미지·모델 manifest로 관리한다. 이번에 패키지를 설치/갱신하지 않았다.

## 6. 부족한 검증과 운영 지표

1. 다중 장치 대상 정확성, 동일 ID 동시 요청, 부분 실패, 결과 순서 역전, 결과 유실, 재시작 후 재전송 테스트.
2. 센서 DB 중단·복구·종료 중 배치 보존, 수동 모드/승인 상태 재시작 유지 시험.
3. 카메라 A/B에 서로 다른 사건을 넣는 temporal 버퍼 격리 시험.
4. 큐 대기시간, EdgeX 발행→서비스 수신→장비 응답→UI 반영 시간을 같은 request ID로 추적. 실제 장비 응답과 사람의 시청각 UAT는 구분.
5. 장치별 성공/실패/timeout/queue depth, 센서 last-seen·원천 시각·수신 시각·DB 저장 시각 표시. “로그가 없음”을 게이트웨이 고장으로 즉시 단정하지 않기.
6. Jetson 부팅, X11/EGL 준비, 필수 서비스/registry 로딩, 모델 파일 존재, 복구 후 정상 처리까지의 smoke 검증.

기존 전광판 UAT 문서의 결과 수신·장비 로그 증거는 유지하되, 그것만으로 스피커·사이렌·다중 장치 격리까지 완료됐다고 확장 해석하지 않는다.

| 발행 콜백만 성공, 장비 결과 없음 | `acknowledged`, `ok=true` |
| board-1 실패 후 board-2 성공 | 논리 명령 한 행이 `acknowledged` |
| EdgeX 모드의 오프라인 스피커 | 직접 TCP 검사 1회 후 대상 제외 |
| EdgeX Action 생성 | 직접 전광판 idle 스레드 시작 호출 1회 |
| 센서 DB insert 실패 후 재flush | 대기 1건→0건, insert 시도 총 1회 |
| 결과 DB 30회 조회 | 열린 파일 디스크립터 증가 0 |

재현에는 가짜 장비·임시 DB를 사용했고, 실제 네트워크 장비는 조작하지 않았다. 임시 재현 스크립트는 `/tmp/cctv-code-audit-scUcd3/reproduce.py`이며 영구 회귀 테스트를 대체하지 않는다.

## 8. 권장 실행 순서와 인수 기준

1. **안전한 변경 기준선:** 기존 작업을 기능별로 구분하고 현 상태/배포본/모델·설정 복구 지점을 기록한다. 실패 테스트의 운영 정책을 바로잡고 재현 결함을 회귀 테스트로 고정한다.
2. **보호와 EdgeX 일원화:** 포트·비밀값 보호, Action 직접 제어 제거, registry 배포, 전광판 제어 주체 단일화. 현장 적용 전에 Compose/API 영향과 롤백을 확인한다.
3. **명령 신뢰도:** 대상 ID·중복 방지·장치별 결과 상태·제한 큐·timeout/TTL을 작은 변경으로 나눈다. 그 뒤 스피커·사이렌 실제 UAT와 다중 장치 장애 격리/롤백 UAT를 시행한다.
4. **복구 가능성:** 센서 DB 내구성, 운영 모드 영속성, readiness와 CI 발행 게이트를 정비한다.
5. **모델·UI 리팩토링:** 학습/추론 특징 공유, 카메라별 검증, 모델 승격 안전장치, UI/API 정지 방지. 이후 동작을 유지하며 큰 파일을 분리한다.
6. **조건부 폐기:** 호출·배포·롤백 참조가 사라진 레거시만 제거한다. 모델 shadow 검증은 장비 출력과 분리해 수행할 수 있으나 자원 경합을 계측한다.

가장 먼저 손댈 업무는 **“장치 제어 보호 + 실제 코드 경로의 EdgeX 일원화”**다. 미관 중심의 파일 정리보다 장애·오작동·잘못된 성공 표시를 먼저 줄이는 편이 현재 현장 문제와 직접 연결된다.

분석에는 `backend-architect`와 `code-review-and-quality` 기준을 적용해, 전체 재작성 대신 경계·상태 계약·실패 복구와 근거 있는 단계별 정리를 우선했다.
